# Ticket classification

Use this reference when proposing work-type or component labels while creating, triaging, or backfilling tickets. It describes the process; a project's `.agents/references/ticket-labels.json`, when present, owns its vocabulary and boundaries. Read that file from the project checkout before classifying. Do not copy one project's catalog to another team.

1. Read the ticket's description, acceptance criteria, and current labels. A title or repository route alone is not enough to settle a component. Treat linked implementation paths as supporting evidence for a retrospective review, not as proof of the original request.
2. Decide whether the record requests delivery or asks for a decision, approval, information, or action. Choose one type from the project's catalog when the evidence supports it. A project may define `ask` as a type for the latter records. Keep that type separate from the workflow marker that routes asks, and from the implementation ticket an ask may block. A bug requires evidence of an existing promised behavior that fails; a new capability is a feature; a new guard is test work, while a broken existing CI contract is a bug. Documentation explains behavior; maintenance publishes or configures it; refactoring preserves it.
3. Select zero or more components whose behavior the requested work materially changes. Allow more than one for independent affected areas. Abstain on an unclear boundary; a path, a generic word, or a test mention alone does not establish ownership. Keep project and initiative relationships, ask/control state, and repository routing separate from these labels.
4. Record the evidence, uncertainty, and any alternative before a backfill. Apply recommendations only within the authorized scope and under a reviewed classification policy. Preserve the ticket's existing work type unless a reviewed correction calls for replacement. Add supported components without removing unrelated labels. Create a label only when that scope and policy authorize it.
5. Before a write, use `writing-to-linear.md` to resolve the live label name, scope, ID or ambiguity through current account access. The project file is policy, not an ID cache. Read back the ticket after a reviewed write.

For cleanup of case-only duplicates, inventory active and archived labels and issues. Check synchronization with linked systems, test a disposable canary, and read back both systems after a delay. A write that appears to remove a duplicate may be reversed by synchronization. Stop broad cleanup until the canary has a stable result.
